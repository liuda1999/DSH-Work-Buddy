## 一、项目概述与功能介绍

DSH Work Buddy 是一个综合性的任务管理与智能体协作平台，由三大组件构成：

### 1.1 组件构成

| 组件 | 目录 | 版本 | 说明 |
|------|------|------|------|
| WorkBuddy-Web | `WorkBuddy-Web/` | 0.1.0 | 任务管理控制台（前端 + 一体化服务） |
| deepseek-harness | `deepseek-harness/deepseek-harness-master/` | 0.1.0-rc.7 | dsh 智能体运行框架 |
| llm-wiki | `llm-wiki/project/` | 3.0.0 | VitePress Wiki 文档组件 |

### 1.2 WorkBuddy-Web 功能清单

- **任务管理**：任务看板、四张 KPI 汇总卡片（今日待办 / 进行中 / 已完成 / 逾期任务，带视频背景，播放速度 0.5 倍）、新建任务（含工作区选择、期限设置）、任务详情、逾期提醒与"设定新期限"恢复、3D 卡牌抽屉
- **我的工作区**：侧边栏工作区列表、新建/删除/切换工作区，与 dsh 智能体工作区同步（`/api/workspaces/sync-harness`）
- **智能体会话**：点击任务打开对话弹窗，iframe 经 `/harness/` 同源代理嵌入 dsh web；含智能体身份选择、任务文件树、上下文压力监控、会话书架、`/compact` 上下文压缩；已完成/逾期任务只读拦截
- **项目总览**：项目状态汇总卡片
- **日程管理**：日程列表（赛博网格背景）
- **资源仓库**：四个 Tab——插件（对接 dsh `agentPreset.list`，展示标准/PTC/极简/创造 4 个智能体预设）、技能、智能体模板（新建/编辑/删除）、Wiki 文档（含知识图谱）
- **插件社区**：网址导航瀑布流卡片
- **设置中心**：DeepSeek 大模型配置（API Key 保存/清除、Flash/Pro 模型预设、MaxTokens/上下文高级设置）、自定义 Provider、插件配置（shell / agent-loop / web-search-deepseek）、凭证管理，全部经网关转发 dsh RPC（`settings.describe` / `settings.mutate` / `credentials.*`）
- **归档**：会话归档分组、归档详情（文件大小、对话轮数）

### 1.3 deepseek-harness 智能体能力

- 智能体生命周期管理、工具调用、会话持久化（`session.jsonl.zstd` 逐事件多帧流）、沙箱安全
- RPC 接口：`workspace.*`、`session.*`（create/prompt/history/cancel/fork...）、`subagent.*`、`skill.list`、`agentPreset.*`、`settings.*`、`credentials.*`、`llm.*`、`host.*`
- 事件流：WebSocket `/api/events.mux`（会话帧）与 `/api/events.host`
- 默认模型：deepseek-v4-flash（provider: deepseek-official）

### 1.4 架构与端口

```
浏览器 ── http://127.0.0.1:8765 ── WorkBuddy-Web server.js（一体化服务）
                                      ├── 静态文件（index.html、card-bg 视频、logo）
                                      ├── 本地业务 API（/api/workspaces、/api/tasks 等）
                                      ├── /harness/ 同源代理 + RPC 转发 + WebSocket 桥接
                                      └── 自动拉起 dsh 智能体（child_process）
                                              └── http://127.0.0.1:3080（dsh web + RPC）
```

- **固定端口约定**：Web = `127.0.0.1:8765`；智能体 = `127.0.0.1:3080`（内部，不对外变化）
- **一键启动**：根目录 `start.bat`（校验 Node → 启用 pnpm → 按需 install/build → 启动 server.js → 打开浏览器）

## 四、存在的问题（错误与教训）

如实记录，按严重程度排序：

### 4.1 【严重】打包清理造成不可逆删除

**事实**：2026-08-20 打包时，按"清理历史归档与临时文件"的方案删除了：
- `WorkBuddy-Web.zip`、`WorkBuddy-Web_0.1.0.zip`、`deepseek-harness-08-18-深度拆解.zip`、`llm-wiki-08-18-深度拆解.tar.gz`
- `E:\worke\0.42.1` 目录
- `audit-*.png` 审计图片

**后果**：回收站被清空 + 磁盘被后续大量写入覆盖（pnpm 安装、构建、两次 46MB zip），数据恢复仅找回 8 个无价值临时脚本，**上述内容永久丢失**。

**注**：`src/`、`assets/`、`output/` 并非被删——经目录时间戳（2026-08-18 21:32:54 创建，created==modified）与会话记忆双重证实，它们创建时即为空的规划目录。

**教训**：删除前无版本控制兜底；删除操作未逐项向用户确认内容清单；此后所有删除类操作必须先经 git 提交形成还原点。

### 4.2 【严重】误判并覆盖完整版 server.js

**事实**：打包阶段读到 server.js 仅 36 行片段（完整版或在此前后丢失），08-21 启动测试时据此误判"仅为静态服务片段"，以 8080 端口的 mock 实现整文件覆盖。而当时完整版服务仍在 8765 运行（含自动拉起智能体、代理全链路）。

**后果**：丢失完整版源码（被迫按运行行为逆向重建）；端口漂移（8765→8080）；对话窗口空白。

**教训**：改文件前未核实"运行中的进程即该文件的完整版"；读取截断内容即下结论。应先探查运行态（netstat/进程命令行）再动源码。

### 4.3 【中】WebSocket 代理三处 bug（重建期引入）

1. `delete headers.connection` 误删了刚设置的 `Connection: Upgrade` → 上游 426
2. 浏览器 Origin（`127.0.0.1:8765`）透传 → dsh 信任围栏 403
3. 上游 101 响应头（含 `Sec-WebSocket-Accept`）未转发给客户端 → 握手失败

**后果**：事件流断连，dsh web 界面渲染残缺（"设计大量丢失"的直接原因）。

### 4.4 【中】代理范围设计不足

初版代理只覆盖 `/harness/` 与 `/api/*`，而 dsh web SPA 的 JS/CSS 是站点根绝对路径（`/assets/`、`/plugins/`）→ 全部 404 → 无输入框。修复后采用"白名单本地资源、其余全转发"策略。

### 4.5 【轻】其他

- PowerShell heredoc / 多行命令多次解析失败，浪费轮次（应及早改用脚本文件）
- 打包脚本临时文件命名混乱（`_*.py`/`_*.mjs`），现已全部纳入 `.gitignore` 并清理
