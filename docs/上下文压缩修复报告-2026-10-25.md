## 一、复核：对原分析文档的三点修正

1. **P0 根因比文档结论更进一步**。`settings.yaml` 里路由级 `contextWindow: 131072` 是**无效键**（`llm-pi-ai/src/config.ts` 路由 schema 只有 `defaultContextWindow`；模型级 `models[].contextWindow` 才是精确声明位）。qwen 模型条目未声明窗口 → 取包级默认 `DEFAULT_CONTEXT_WINDOW = 262_144`（`config.ts:38`），且该值曾被设置页**固化写入存储**（实测 dump：`defaultContextWindow: 262144`）。因此：
   - 262144 不是谁手滑填的，是默认值踢进来的；
   - **用户此前把 yaml 改成 131072 是空操作**（未知键被静默忽略，schemastery 与 resolveProfiles 均不拒绝未知键），修复前线上生效窗口一直是 262144。
2. **"剪枝器未装配"不成立**。`tool-result-pruner` 在 base bundle 与 standard 预设中均已挂载（8192/4096/1024）。但 web-app bundle 把宿主行禁用，压缩三件套改在**智能体预设的隔离域**内按会话挂载（`apps/cli/config/agent-presets/standard/agent.cordis.yml:137-155`）——所以压缩参数的合法配置通道是**用户预设**（`~/.dsh/.agent-presets/`，roster 每次调用重读磁盘，无需重启），不是 settings.yaml（compaction-basic 未注册 settings 节），也不是 profile patch（那只作用于宿主树）。
3. **"摘要请求不携带工具 schema"建议否决**。`compaction-basic/src/summarizer.ts:21-30` 注释明确：携带完整 system+tools+消息前缀是为了让摘要调用成为上一请求的**真前缀**、复用 llama.cpp KV cache。去掉 tools 省几千 token，代价是 20 万 token 前缀缓存全失效，对本地推理是负优化。

### B. P4 落地：用户预设 `standard-fix`

`~/.dsh/.agent-presets/standard-fix/`（复制 shipped standard 后修改，roster 即时发现）：

- `tool-result-pruner`：`thresholdChars 8192→2048 / headChars 4096→1024 / tailChars 1024→512`（原分析实测：prefill 降约 24%；纯字符裁剪无模型调用，原始事件日志完整保留）

## 六、追加验证：上下文窗口动态跟随（2026-10-25 夜）

针对「换 API 后是否按新窗口提前压缩」的验收问题，补充四组实测：

| 实验 | 结果 |
|---|---|
| 会话中途热改窗口 131072→12288→10240 | `request/context` 记录 `[131072, 10240]`——下一请求立即按新窗口，不沿用旧值；阈值随之为 0.8×新窗口 |
| 窗口缩小后模型输出预算也随之收缩 | 实测长文生成受限（thinking 模型输出预算被小窗口压缩）——证明窗口热切换被请求层全链路遵守 |
| 短消息小会话 + 低阈值 | 不触发：可压区（消息面 − 保留尾 16%）为空时压缩器静默等待（设计行为，`selectCompactableRange` 返回 null） |
| 真长文 + 低阈值（复现 10-18 会话条件） | turn2 边界 `compaction/start {turn:2}` 触发——重启后压力机制正常 |

**结论**：压缩阈值每回合按「当前路由模型的声明窗口」重算（`compactIfNeeded` 每次经 `resolveModelInfo` 解析当前 provider/model）。换模型（selectModel）或热改 settings 均在下一回合生效。**窗口取声明值而非端点探测值**——换 API 时须同步更新 settings 中该模型的 `contextWindow`（声明改小只会提前压缩，安全；声明偏大不更新则回到原故障模式，仅剩溢出恢复兜底，standard-fix 预设下 maxOverflowRetries=2）。
